# Схема данных

Сырые данные прогонов в git не попадают (QLT-5). Здесь описан их формат.

## Каталог прогона

`bench run` пишет каждый прогон в свой каталог, по умолчанию `out/<время UTC>-<транспорт>-<сеть>-<нагрузка>-s<сид>/`, например `out/20261021T101500Z-quic-interregion-small-s1/`. Как идёт прогон — в [методике](../docs/methodology.md#прогон-gen-6-gen-7).

| Файл | Что в нём |
| --- | --- |
| `calls.csv` | вызовы, см. ниже |
| `meta.json` | параметры, окружение, CPU и сводка, см. ниже |
| `server.log`, `client.log` | stderr сервера и клиента; в `client.log` — сводка генератора |
| `certs/` | сертификаты прогона |

## calls.csv

Одна строка на вызов, сообщение bidi-стрима или установку соединения (GEN-4). Пишет `bench load`, строки идут в порядке расписания.

| Колонка | Тип | Смысл |
| --- | --- | --- |
| `seq` | целое | номер события в расписании прогона, с 0 |
| `kind` | строка | `small` — мелкий unary-вызов, `heavy` — тяжёлый, `echo` — сообщение bidi-стрима, `connect` — установка соединения |
| `scheduled_ns` | целое, нс | когда событие было запланировано, от начала прогона |
| `latency_ns` | целое, нс | от запланированного момента до ответа или до ошибки |
| `code` | целое | статус в нумерации gRPC: 0 — OK, 1 — Canceled, 4 — DeadlineExceeded, 14 — Unavailable и т. д. |
| `req_bytes` | целое | размер payload запроса |
| `resp_bytes` | целое | размер полученного payload ответа; 0 при ошибке |
| `conn` | целое | соединение: 0 — единственное соединение прогона, n — n-е соединение профиля с переподключениями |
| `phase` | строка | `warmup` — вызов запланирован в прогреве, `measure` — в измерении |

Подробности:

- Задержка считается от запланированного, а не от фактического момента отправки. Если генератор или транспорт задержали отправку, это входит в задержку.
- `connect`: задержка — время установки соединения (EXP-6): для QUIC handshake, для gRPC TCP, TLS и обмен настройками HTTP/2. Вызовы этого соединения запланированы на тот же момент и отправляются после установки, поэтому их задержка включает установку соединения.
- `echo`: задержка — от запланированной отправки сообщения до возврата его копии. Сообщение, которое не вернулось за тайм-аут, записано с кодом 4 и задержкой, равной тайм-ауту.
- Вызов, не получивший ответа до дедлайна (10 с от запланированного момента), записан с кодом 4. Вызовы, которые прерванный прогон не успел отправить, записаны с кодом 1.
- В режиме closed-loop (`bench load -closed N`) `scheduled_ns` — фактический момент отправки: расписания там нет.

## meta.json

Всё о прогоне, кроме самих вызовов (GEN-6, GEN-7). Длительности — целые наносекунды в полях с суффиксом `_ns`, моменты времени — RFC 3339 в UTC.

| Поле | Смысл |
| --- | --- |
| `run_id` | имя каталога прогона |
| `transport` | `quic` или `grpc-h2` |
| `network` | профиль сети: `name`, `description`, `rtt_ns`, `jitter_ns`, `loss_pct` (потери в процентах), `loss_burst`, `reorder_pct`, `rate_bps` (бит/с, 0 — без ограничения), `queue_bdp`, `outage` (`duration_ns`, `every_ns`) |
| `load` | профиль нагрузки: `name`, `description` и те части, что есть: `small` (`rate` в секунду, `min_size`, `max_size` в байтах), `heavy` (`size`, `every_ns`), `echo` (`rate`, `size`), `reconnect` (`every_ns`, `calls`) |
| `tcp` | вариант TCP: `aligned` или `default` |
| `seed`, `warmup_ns`, `measure_ns`, `timeout_ns` | сид, прогрев, измерение и дедлайн вызова |
| `outages_ns` | запланированные начала обрывов связи от начала расписания |
| `build` | `go` — версия Go; `commit`, `dirty` — git-коммит и были ли незакоммиченные изменения; `commit_source` — откуда они: `binary` (вшиты `go build`) или `git`, пусто, если коммит не знает ни бинарь, ни git (сборка не из клона); `modules` — версии модулей сборки |
| `env` | окружение: машина, инструменты и стенд, как печатает `testbed env` |
| `problems` | отличия машины от NET-5; на настроенной машине пусто |
| `server`, `client` | `cpus` — заданные ядра (пусто — без закрепления), `cpus_allowed` — ядра, на которых процессу разрешено работать, `env` — переменные `GOMAXPROCS`, `GOGC`, `GOMEMLIMIT`, `GODEBUG` и `QUIC_GO_*` процесса, `cpu` — его время `user_ns` и `system_ns` за окно |
| `orchestrator` | `cpus_allowed` оркестратора |
| `tls` | согласованные настройки TLS: `version`, `cipher_suite`, `group`; ожидается одна запись |
| `window` | окно измерения глазами оркестратора: `start`, `measure`, `end` — когда генератор сообщил о начале прогрева, начале и конце измерения; `duration_ns` — время между замерами CPU |
| `cores` | по каждому логическому CPU машины время за окно: `id`, `user_ns`, `nice_ns`, `system_ns`, `idle_ns`, `iowait_ns`, `irq_ns`, `softirq_ns`, `steal_ns` |
| `results` | сводка измерения: `kinds` (`kind`, `count`, `errors`, `p50_ns`, `p99_ns`), `sent_bytes_per_s` и `received_bytes_per_s`, `in_flight_mean` и `in_flight_max` |

Подробности:

- CPU записан с точностью 10 мс: в таких единицах его считает `/proc`. Почему записаны и процессы, и ядра, — в методике.
- `results` считаются по строкам `calls.csv` с `phase` = `measure`. Goodput — байты payload успешных вызовов и сообщений, отправленные и полученные, делённые на длительность измерения. Вызов в полёте — от запланированного момента до ответа или ошибки; считается только время внутри окна измерения, без установки соединений.
