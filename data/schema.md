# Схема данных

Сырые данные прогонов в git не попадают (QLT-5). Здесь описан их формат.

## Каталог прогона

`bench run` пишет каждый прогон в свой каталог, по умолчанию `out/<время UTC>-<транспорт>-<сеть>-<нагрузка>-s<сид>/`, например `out/20261021T101500Z-quic-interregion-small-s1/`. Как идёт прогон — в [методике](../docs/methodology.md#прогон-gen-6-gen-7).

| Файл | Что в нём |
| --- | --- |
| `calls.csv` | вызовы, см. ниже |
| `meta.json` | параметры, окружение, CPU и сводка, см. ниже |
| `server.log`, `client.log` | stderr сервера и клиента; в `client.log` — сводка генератора |
| `certs/` | сертификаты прогона |

## Каталог серии

`bench series` кладёт серию в свой каталог, по умолчанию `out/<время UTC>-<имя матрицы>/`, например `out/20261026T200000Z-pilot/`. Как идёт серия — в [методике](../docs/methodology.md#серия-exp-2-exp-5-exp-8).

| Файл | Что в нём |
| --- | --- |
| `series.json` | постановка и план серии, см. ниже |
| `<прогон>/` | каталог прогона, как выше |
| `check/` | отчёты самопроверки стенда `<время>-<сеть>.json` в формате `testbed check -json`, по одному на сеть при каждом запуске серии |
| `failed/` | остатки упавших и прерванных прогонов, `<прогон>-<время>` |

Поля `series.json`:

| Поле | Смысл |
| --- | --- |
| `matrix` | матрица, как её прочитала серия: `name`, `seed`, `repeats`, `warmup_ns`, `duration_ns`, `variants` (`name`, `transport`, `tcp`, `pool_size`, `pool_policy`, `max_recv_msg_bytes`, `max_send_msg_bytes`), `networks`, `loads`, `drift` |
| `networks`, `loads` | профили сетей и нагрузок серии на момент её начала, в формате полей `network` и `load` из `meta.json` |
| `created` | когда серия началась |
| `runs` | прогоны в порядке выполнения: `id` — имя каталога (номер, вариант, сеть, нагрузка и `r<повтор>` или роль), `variant`, `transport`, `tcp`, `pool_size`, `pool_policy`, `max_recv_msg_bytes`, `max_send_msg_bytes`, `network`, `load`, `repeat` (с 1, у прогонов дрейфа 0), `seed`, `role` (`drift-start`, `drift-end` или нет) |

| `report.md`, `fig*.png` | — | сводка главных чисел и рисунки |

## Отчёт основной серии (Q-06)

`make plots-main MAIN_SERIES=DIR` читает сырые блоки Q-05 по одному прогону.
Имена подкаталогов совпадают с именами YAML-файлов без `.yaml`, поле
`matrix.name` имеет префикс `main-`. Учитываются `series.json` и завершённые
прогоны с `meta.json` и `calls.csv`. Отсутствие целого плана видно в таблице
готовности. Для существующего плана отсутствие `meta.json` означает
незавершённый прогон. План проверяется по набору ячеек и повторов, порядку
дрейфа, комплектам вариантов и настройкам. Метаданные сверяются с планом.
Идентификатор прогона локален для матрицы. Ключ — `(series, run_id)`.

| Файл | Строка и важные поля |
| --- | --- |
| `coverage.csv` | `series`, `planned`, `finished`, `missing`, `status` (`no-plan`, `partial`, `complete`). Считаются и прогоны дрейфа |
| `missing_runs.csv` | Каждый недостающий прогон с известным ID из загруженного плана |
| `runs.csv` | Метаданные завершённых прогонов с дополнительным `series` |
| `run_metrics.csv` | Прогон и вид вызова, перцентили в мс, счётчики и доля ошибок, рост, перегрузка, прогрев и CPU. CPU на вызов использует общее число записей измерения прогона |
| `latency.csv` | Матрица, сеть, нагрузка, вид, вариант и `metric` (`p50`, `p95`, `p99`), число `runs` и `expected`, ошибки, перегрузка, `median`, `lo`, `hi` в мс и `samples` |
| `cpu.csv` | Матрица, сеть, нагрузка, вариант и одна из четырёх метрик CPU. Оценки в мкс на вызов |
| `connections.csv` | Строки `connect` из `latency.csv` с дополнительными `median_rtt`, `lo_rtt`, `hi_rtt` в долях RTT |
| `grid.csv`, `reorder.csv` | Одна строка на точку и нагрузку. `median`, `lo`, `hi` — отношение p99 QUIC к gRPC/HTTP/2 для полной ячейки без перегрузки. `regime` объясняет пропуск отношения |
| `hypotheses.csv` | Вердикты `accepted`, `rejected`, `insufficient` для H1–H6 и отдельно для H6a/b/c, числа поддержанных, отвергнутых, неопределённых и исключённых ячеек |
| `hypothesis_cells.csv` | `family`, условие, метрика, ожидаемые и наблюдаемые повторы, `outcome` (`support`, `oppose`, `inconclusive`, `excluded`) и код основания `reason`. Для сравнения пары также медианы, `ratio = 1 + E`, границы `ratio_lo`, `ratio_hi`, p и `p_holm` |
| `hypothesis_contrasts.csv` | Совместные контрасты G, S в мс и D без единицы. `estimate`, обычные 95%-границы `lo`, `hi` и границы решения `adjusted_lo`, `adjusted_hi` |
| `hypothesis_cpu.csv` | H4 по сети и четырём оценкам CPU, медианы и исход проверки лимита |
| `transport_recommendations.csv` | 20 сочетаний составной сети и нагрузки. Перцентили, goodput обеих сторон и их интервалы/поправки, четыре отношения CPU, `decision`, `preferred`, `reason` |
| `warmup.csv`, `drift.csv` | Оценки прогрева и дрейфа с привязкой к матрице. Пустой `head_ratio` означает, что сравнить части окна невозможно |
| `bulk_runs.csv`, `bulk.csv` | Строки конечных передач и сводки по успешным прогонам. Схема bulk приведена ниже |
| `q04_micro.csv`, `q04_early_gain.csv` | Сводки отдельного Q-04, если передан `MAIN_MICRO=DIR` с готовыми `meta.json` и `raw/` |
| `report.md`, `*.png`, `artifacts.json` | Сводка, графики и список файлов, созданных текущим запуском |

Для описательных интервалов нужны хотя бы два прогона. Для вердикта нужны
все повторы каждого сравниваемого варианта. Прогоны дрейфа исключены из
статистических ячеек. В неполном сравнении `p = 1` удерживает прежний размер
семейства Холма, это служебное значение. H3 и H5 пересчитываются по целым
тройкам повторов с фиксированным размером семейства Бонферрони. Таблицы
выводятся после решений с сохранением точности. Старый `make plots`
по-прежнему обслуживает отдельные серии и данные пилота.

## Пилотные данные

[`data/pilot`](pilot) — таблицы анализа пилота ([итоги](../docs/pilot.md)) в формате выше, его `report.md` и рисунки, план `series.json` и отчёты самопроверки стенда `check/`. Все вызовы (`calls.parquet`, 25 МБ) в git не помещаются и лежат во вложении релиза (QLT-5). С ним таблицы и рисунки пересобираются с нуля:

```sh
# calls.parquet из релиза — в data/pilot
make plots ANALYSIS=data/pilot
```

## Сбор micro (Q-04)

Отдельный от `bench series` формат `make bench-micro`. По умолчанию каталог
`out/micro-<время UTC>/`, либо новый `--out DIR`. Он содержит два семейства:
`overhead` (4 эталона × 2 шаблона × 4 размера) и `reconnect` (2 RTT × 3 режима).
Матрицы проверяются полностью в каждом процессе; старые двухрежимные выводы
RPC-14 не выдаются за новый формат. Возобновление и перезапись не предусмотрены.

| Путь | Содержание |
| --- | --- |
| `meta.json` | ready marker, `schema_version=1`, `kind=rpc-micro`, UTC начала/окончания, `config`, `environment`, `git`, `builds`, `jobs`, SHA-256 исходников и архива |
| `raw/<order>-<family>.txt` | объединённый stdout/stderr benchmark-процесса, обычный текст Go benchmark |
| `provenance/` | commit/status, Go version/env, `modules-root.txt`, `modules-rpc.txt`, `modules-grpcbridge.txt`, команды сборки в `meta.builds` и их выводы, build info, `sources.json` (путь → SHA-256), `sources.tar.gz` |
| `bin/` | два собранных без race detector benchmark-бинарника |
| `failed.json` | причина и накопленные метаданные незавершённого сбора; сырые выводы остаются, `meta.json` отсутствует |
| `pending.json` | временные метаданные для проверки всей матрицы перед атомарным переименованием в `meta.json` |
| `analysis/benchmarks.csv` | одна строка на случай и повтор: параметры, число операций, исходные метрики |
| `analysis/summary.csv` | одна строка на случай и метрику: `repeats`, `median`, `lo`, `hi` |
| `analysis/early_gain.csv` | на каждый `rtt_ms`: `repeats`, парный выигрыш `gain_ms`, `gain_lo_ms`, `gain_hi_ms`, `gain_rtts` |
| `analysis/report.md` | сводка с условиями и ограничениями |

`config`: `repeats`, `cpu` (GOMAXPROCS), `benchtime` (только overhead),
`reconnect_iterations`, `seed`. `jobs` содержит `family`, `repeat` с 1,
`order` с 1, команду массивом аргументов, cwd, UTC начала, длительность в
секундах, returncode, относительный путь `raw` и `raw_sha256`. Сбой процесса
или таймаут оставляет вывод и причину в `failed.json`; провалившийся процесс
может не входить в список успешно собранных `jobs`. Источники сохраняются
из трёх модулей и Python: Go/proto/Python/YAML, module-файлы, Makefile,
requirements и descriptor fixtures, включая новые неигнорируемые файлы.
Полное окружение процесса и игнорируемые секреты не копируются.

Группировка таблиц: `(family, backend, kind, payload_bytes, rtt_ms, mode, cpu)`.
Для памяти `mode` пустой, `rtt_ms=0`; для reconnect `backend=quic`,
`kind=unary`, `payload_bytes=8`. `ns_per_op`, `bytes_per_op`, `allocs_per_op`
соответствуют `ns/op`, `B/op`, `allocs/op`; последние две характеризуют общий
benchmark-процесс, не отдельный клиент. Для reconnect исходные `first_reply_ns`
переводятся в `first_reply_ms`, а напечатанные `first_reply_ms` и `RTT/reply`
сверяются с учётом округления Go. Также проверяются `did_resume`, `used_0rtt`,
`reported_rtt_ms`, `reported_payload_bytes`, `tls_version`, `tls_curve`,
`tls_cipher_suite`. Сырой вывод, его SHA-256, CPU, число reconnect-операций,
полнота повторов и порядок проверяются при каждом чтении.

`median` и границы — по средним отдельных процессов, без веса по числу
операций. Значение `metric` задаёт единицу: `ns_per_op`, `bytes_per_op`,
`allocs_per_op`, `first_reply_ms`. При одном повторе `lo`/`hi` пусты; при RTT 0
`gain_rtts` пуст. Перестроение: `PYTHONPATH=analysis/plots .venv/bin/python
-m qrpcplots micro DIR [-o OUT]`. Эти таблицы не объединяются с `runs.csv`,
`calls.parquet`, bulk или пилотом.

## calls.csv

Одна строка на вызов, сообщение bidi-стрима или установку соединения (GEN-4). Пишет `bench load`, строки идут в порядке расписания.

| Колонка | Тип | Смысл |
| --- | --- | --- |
| `seq` | целое | номер события в расписании прогона, с 0 |
| `kind` | строка | `small` — мелкий unary-вызов, `heavy` — тяжёлый, `echo` — сообщение bidi-стрима, `connect` — установка соединения; `bulk` — конечная передача объекта |
| `scheduled_ns` | целое, нс | когда событие было запланировано, от начала прогона |
| `latency_ns` | целое, нс | от запланированного момента до ответа или до ошибки |
| `code` | целое | статус в нумерации gRPC: 0 — OK, 1 — Canceled, 4 — DeadlineExceeded, 14 — Unavailable и т. д. |
| `req_bytes` | целое | размер payload запроса |
| `resp_bytes` | целое | размер полученного payload ответа; 0 при ошибке |
| `conn` | целое | логический клиент (одно соединение или пул): 0 — основной клиент прогона, n — n-й новый клиент профиля переподключений; физическое соединение внутри пула здесь не нумеруется |
| `chunks` | целое | полученные сообщения bulk, включая сообщения до ошибки; 0 у остальных видов; последняя колонка, отсутствует в старых CSV |
| `phase` | строка | `warmup` — вызов запланирован в прогреве, `measure` — в измерении |

Подробности:

- Задержка считается от запланированного, а не от фактического момента отправки. Если генератор или транспорт задержали отправку, это входит в задержку.
- `connect`: задержка — время установки соединения (EXP-6): для QUIC handshake, для HTTP/2 TCP, TLS и настройки HTTP/2; для HTTP/3 полный QUIC handshake и настройки HTTP/3. Для `grpc-h2-pool` это готовность всех N соединений, устанавливаемых параллельно. Вызовы этого клиента запланированы на тот же момент и отправляются после установки, поэтому их задержка включает установку соединения.
- `echo`: задержка — от запланированной отправки сообщения до возврата его копии. Сообщение, которое не вернулось за тайм-аут, записано с кодом 4 и задержкой, равной тайм-ауту.
- Вызов, не получивший ответа до дедлайна (10 с от запланированного момента), записан с кодом 4. Вызовы, которые прерванный прогон не успел отправить, записаны с кодом 1.
- В режиме closed-loop (`bench load -closed N`) `scheduled_ns` — фактический момент отправки: расписания там нет.

## meta.json

Всё о прогоне, кроме самих вызовов (GEN-6, GEN-7). Длительности — целые наносекунды в полях с суффиксом `_ns`, моменты времени — RFC 3339 в UTC.

| Поле | Смысл |
| --- | --- |
| `run_id` | имя каталога прогона |
| `transport` | `quic`, `grpc-h2`, `grpc-h2-pool`, `grpc-h3` или `connect-h2` |
| `pool_size`, `pool_policy` | фактическое число соединений и распределение RPC: для пула N и `round-robin`, для остальных транспортов 1 и `single` |
| `max_recv_msg_bytes`, `max_send_msg_bytes` | пределы сериализованного сообщения в байтах, одинаковые у клиента и сервера; отправка `0` — без отдельного ограничения |
| `network` | профиль сети: `name`, `description`, `rtt_ns`, `jitter_ns`, `loss_pct` (потери в процентах), `loss_burst`, `reorder_pct`, `rate_bps` (бит/с, 0 — без ограничения), `queue_bdp`, `outage` (`duration_ns`, `every_ns`) |
| `load` | профиль нагрузки: `name`, `description` и те части, что есть: `small` (`rate` в секунду, `min_size`, `max_size` в байтах), `heavy` (`size`, `every_ns`), `echo` (`rate`, `size`), `reconnect` (`every_ns`, `calls`) |
| `tcp` | вариант TCP: `aligned` или `default` |
| `seed`, `warmup_ns`, `measure_ns`, `timeout_ns` | сид, прогрев, измерение и дедлайн вызова |
| `outages_ns` | запланированные начала обрывов связи от начала расписания |
| `build` | `go` — версия Go; `commit`, `dirty` — git-коммит и были ли незакоммиченные изменения; `commit_source` — откуда они: `binary` (вшиты `go build`) или `git`, пусто, если коммит не знает ни бинарь, ни git (сборка не из клона); `modules` — версии модулей сборки |
| `env` | окружение: машина, инструменты и стенд, как печатает `testbed env` |
| `problems` | отличия машины от NET-5; на настроенной машине пусто |
| `server`, `client` | `cpus` — заданные ядра (пусто — без закрепления), `cpus_allowed` — ядра, на которых процессу разрешено работать, `env` — переменные `GOMAXPROCS`, `GOGC`, `GOMEMLIMIT`, `GODEBUG` и `QUIC_GO_*` процесса, `cpu` — его время `user_ns` и `system_ns` за окно |
| `orchestrator` | `cpus_allowed` оркестратора |
| `tls` | согласованные настройки TLS: `version`, `cipher_suite`, `group`, `alpn`; ожидается одна запись. В старых данных `alpn` отсутствует |
| `window` | окно измерения глазами оркестратора: `start`, `measure`, `end` — когда генератор сообщил о начале прогрева, начале и конце измерения; `duration_ns` — время между замерами CPU |
| `cores` | по каждому логическому CPU машины время за окно: `id`, `user_ns`, `nice_ns`, `system_ns`, `idle_ns`, `iowait_ns`, `irq_ns`, `softirq_ns`, `steal_ns` |
| `results` | сводка измерения: `kinds` (`kind`, `count`, `errors`, `p50_ns`, `p99_ns`), `sent_bytes_per_s` и `received_bytes_per_s`, `in_flight_mean` и `in_flight_max` |

Подробности:

- CPU записан с точностью 10 мс: в таких единицах его считает `/proc`. Почему записаны и процессы, и ядра, — в методике.
- `results` считаются по строкам `calls.csv` с `phase` = `measure`. Goodput — байты payload успешных вызовов и сообщений, отправленные и полученные, делённые на длительность измерения. Вызов в полёте — от запланированного момента до ответа или ошибки; считается только время внутри окна измерения, без установки соединений.

Поля `pool_size` и `pool_policy` в старых сериях и `runs.csv` могут отсутствовать: для исторических `quic` и `grpc-h2` это 1 и `single`. Для `grpc-h2-pool` анализ требует явные параметры и их совпадение между планом и `meta.json`. Одно имя `variant` не может объединять разные N или политики. Размер пула и политика входят в проверку постановки при возобновлении серии.

Для `grpc-h3` и `connect-h2` размер пула равен 1, политика — `single`. Параметр `alpn` из TLS сохраняется в новых `runs.csv`; при его наличии анализ проверяет соответствие транспорту, чтобы не принять HTTP/2 за HTTP/3. Версии connect-go и QPACK находятся в `build.modules`.


Лимиты сообщений `max_recv_msg_bytes` и `max_send_msg_bytes` — эффективные
пределы сериализованного protobuf в байтах. Они одинаковы для клиента и сервера
прогона и сохраняются у каждого варианта матрицы, в `runs` плана, в `meta.json`
и `runs.csv` (далее наследуются `summary.csv` и `warmup.csv`). Предел приёма
положительный: 65…2 147 483 647; предел отправки — тот же диапазон либо `0`
(нет отдельного ограничения). Это не размер полезного payload, потока или окна
flow control. Пример для полезного ответа 8 МиБ: оба значения 9 437 184.

У исторических записей и таблиц могут отсутствовать **оба** поля: анализ
восстанавливает прежний приём 4 194 304 и отправку `0`, не переписывая данные.
Частично заданные, некорректные и отличающиеся между планом и метаданными
значения отклоняются. Разные лимиты внутри одного `variant` запрещены, как и
изменение лимитов при возобновлении серии.


## Конечная передача bulk

Профиль `load.bulk` содержит `total_bytes`, `chunk_bytes` и `timeout_ns`.
Те же настройки сохраняются в `series.json` среди определений нагрузок;
изменение любого поля запрещает resume прежней серии. Для bulk `warmup_ns`
в `meta.json` — фактический момент измеряемой попытки относительно начала
прогрева, `measure_ns` — её длительность до конечного статуса, `timeout_ns` —
бюджет передачи. `configured_warmup_ns` и `configured_measure_ns` сохраняют
запрошенные значения; нулевой configured warmup может быть опущен.
`connect_timeout_ns` сохраняет отдельный бюджет установки соединения.
`window.duration_ns` — фактическое окно проб CPU с подтверждением границ.

`results.bulk` содержит `total_bytes`, `chunk_bytes`, `received_bytes`, `chunks`,
`duration_ns`, `code`, `completed`. Последнее поле истинно только после точного
числа байтов/блоков и конечного OK, не просто после последнего payload.
`results.received_bytes_per_s` содержит goodput только успешного объекта;
у ошибочной передачи он нулевой, частичные байты остаются в `results.bulk`.

В CSV одна строка на попытку передачи, не на блок. У измеряемой строки
`kind=bulk`, `phase=measure`; `scheduled_ns` совпадает с фактическим `warmup_ns`,
`latency_ns` — с `measure_ns`, `resp_bytes` и `chunks` содержат реально полученные
полные сообщения, включая данные до ошибки. `req_bytes=0` — у запроса нет
полезной нагрузки; служебный protobuf с размерами в goodput не включается.
Попытки прогрева имеют `phase=warmup`. Чтение старого CSV из девяти колонок
поддерживается; строка bulk требует новую колонку `chunks`.

В `runs.csv` добавлены `bulk_total_bytes`, `bulk_chunk_bytes`, `bulk_timeout_ns`,
`bulk_received_bytes`, `bulk_chunks`, `bulk_duration_ns`, `bulk_code`,
`bulk_completed`. У старых и обычных прогонов это 0/false. План, профиль,
результат метаданных и единственная измеряемая строка CSV проверяются на
совпадение. При чтении/записи таблиц проверка повторяется; смешивать размеры
или таймауты под одной парой `(variant, load)` нельзя.

Отчёт bulk отделён от open-loop перцентилей и правил перегрузки:

| Файл | Содержание |
| --- | --- |
| `bulk_runs.csv` | строка на попытку/прогон: параметры и исходные CPU/результаты из `runs.csv`, `duration_s`, `observed_mbps` (частичный payload / время до статуса), `goodput_mbps` (только успешные), `server_cpu_us_per_mib`, `client_cpu_us_per_mib`, `server_cores_us_per_mib`, `client_cores_us_per_mib` |
| `bulk.csv` | `(network, load, variant, bulk_total_bytes, bulk_chunk_bytes, bulk_timeout_ns)`, `runs`, `completed`, `errors`; для завершённых прогонов медианы `duration_s`, `goodput_mbps`, четырёх оценок CPU на МиБ и их bootstrap-границы с суффиксами `_lo` / `_hi` |

В `bulk_runs.csv` частичные байты дают наблюдаемую скорость и CPU на доставленный
МиБ; при нуле байтов CPU на МиБ отсутствует. Ошибочные передачи исключены из
агрегированных оценок успешной передачи и сохраняются в числе ошибок. Дрейф
сохранён в таблице отдельных прогонов и исключён из агрегированной.
При единственном успешном прогоне bootstrap-границы отсутствуют: вариабельность
по прогонам оценить нельзя. Старые пилотные данные и их файлы не переписываются.
