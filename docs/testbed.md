# Стенд эмуляции сети

Стенд воспроизводит плохую сеть между клиентом и сервером на одной Linux-машине: три network namespace, соединённые парами veth, и `tc netem` на маршрутизаторе. Код — в [`testbed/netns`](../testbed/netns), самопроверка — в [`testbed/selfcheck`](../testbed/selfcheck), профили сети — в [`testbed/scenarios/profiles.yaml`](../testbed/scenarios/profiles.yaml).

## Топология

```text
client                       router                                       server
eth0 10.0.1.2 ──── toclient 10.0.1.1                toserver 10.0.2.1 ──── eth0 10.0.2.2

клиент → сервер:   toclient ─▶ fromclient (ifb): netem ─▶ toserver: tbf ─▶ сервер
сервер → клиент:   toserver ─▶ fromserver (ifb): netem ─▶ toclient: tbf ─▶ клиент
```

Пакет от клиента к серверу приходит на `toclient`, перенаправляется в устройство `fromclient` (ifb), где netem его задерживает, теряет или переставляет, затем маршрутизируется и уходит через `toserver`, где стоит узкое место (tbf). Обратное направление устроено так же: `toserver` → `fromserver` → `toclient`.

Воздействия стоят только на маршрутизаторе (NET-1, NET-3). Если поставить netem на интерфейс самого клиента или сервера, отброшенный в локальной очереди пакет увидит TCP-стек отправителя и среагирует как на перегрузку у себя, а QUIC такого сигнала не получит.

## Запуск

Root не нужен:

```sh
make testbed-shell PROFILE=interregion            # шелл внутри стенда
make testbed-check                                # самопроверка всех профилей, около 2,5 минуты
go run ./testbed/cmd/testbed run -profile congested -- ./bench.sh
go run ./testbed/cmd/testbed check -profile degraded -json report.json
go run ./testbed/cmd/testbed profiles             # список профилей
go run ./testbed/cmd/testbed show degraded        # команды tc профиля, без запуска
```

Внутри стенда программы запускаются в нужном namespace через `ip netns exec client …` и `ip netns exec server …`, а профиль меняется командой `testbed apply ИМЯ`. Сервер доступен клиенту по адресу `10.0.2.2`.

Как это работает: `testbed` перезапускает себя в новых user-, mount- и network-namespace. В них процесс — root и может создавать namespace, veth и qdisc, а у хоста ничего не меняется. Список namespace для `ip netns` лежит в собственном tmpfs поверх `/run/netns`. Стенд живёт, пока работает команда, и исчезает вместе с ней, даже после падения, поэтому следов не остаётся и повторный запуск всегда начинается с чистого места. Из соседнего терминала `ip netns` стенд не видит.

Нужны `ip` (iproute2), `tc`, `ethtool`, `sysctl`, для самопроверки — `ping` и `iperf3`, и разрешённые непривилегированные user namespace. Ubuntu 24.04 по умолчанию их запрещает:

```sh
sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0   # до перезагрузки
echo 'kernel.apparmor_restrict_unprivileged_userns = 0' | sudo tee /etc/sysctl.d/60-userns.conf   # насовсем
```

## Профили

Значения профиля относятся к каждому направлению, кроме RTT: он делится пополам между направлениями. Так, при `loss: 1%` теряется 1% пакетов в каждую сторону, и пара запрос-ответ теряет примерно 2%.

| Поле | Смысл |
| --- | --- |
| `rtt` | время в пути туда и обратно; по `rtt/2` в каждом направлении |
| `jitter` | стандартное отклонение задержки в одну сторону, нормальное распределение; порядок пакетов сохраняется |
| `loss` | доля потерянных пакетов |
| `loss_burst` | средняя длина пачки потерь в пакетах; без поля потери независимы |
| `reorder` | доля пакетов, которые обгоняют отправленные до них |
| `rate` | полоса узкого места, например `100Mbit`; без поля полоса не ограничена |
| `queue_bdp` | очередь узкого места в BDP, то есть в `rate × rtt` |

Значения профилей пока предварительные и уточняются после пилота (фаза 2). Профиль `none` — без воздействий.

## Как устроены воздействия

В каждом направлении два qdisc на разных устройствах:

```text
ifb (fromclient, fromserver)   netem: задержка, джиттер, потери, перестановки; очередь 100 000 пакетов
выход (toserver, toclient)     tbf: полоса и очередь узкого места, если в профиле есть rate, иначе без очереди
```

- **Задержка и джиттер.** netem задерживает каждый пакет на `rtt/2` плюс случайную добавку с нормальным распределением и стандартным отклонением `jitter`. При случайной задержке netem сам переставляет пакеты: поздний пакет обгоняет ранний, если тому выпала задержка больше. Чтобы джиттер не смешивался с перестановками (NET-2), вместе с джиттером netem получает `rate 100gbit`. С этим параметром он не отправит пакет раньше, чем пакет перед ним, а сама полоса так велика, что ничего не ограничивает.
- **Перестановки.** `reorder X%` отправляет X% пакетов без задержки, и они обгоняют пакеты, отправленные за предыдущие `rtt/2`.
- **Потери пачками.** Используется модель Гилберта (`loss gemodel p r`): в «плохом» состоянии теряется каждый пакет, в «хорошем» — ни один. Пачка длится в среднем `1/r` пакетов, а доля времени в плохом состоянии `p/(p+r)` равна доле потерь. Отсюда `r = 1/loss_burst`, `p = loss·r/(1−loss)`. Например, 2% пачками по 4 пакета дают `p ≈ 0,51%`, `r = 25%`.
- **Полоса и очередь** — у tbf, а не у netem. Лимит очереди netem считает все пакеты, которые ждут своей задержки. На «Межрегионе» (100 Мбит/с, 75 мс в одну сторону) таких около 625 пакетов по 1500 байт, и очередь из `limit` у netem вышла бы вдвое меньше заданной, причём её размер менялся бы с RTT и размером пакетов. Очередь tbf задана в байтах и равна `queue_bdp × rate × rtt`, а корзина токенов — одна миллисекунда на полосе узкого места, но не меньше двух полных кадров.
- **Почему netem и tbf на разных устройствах.** Переставленные пакеты netem выдаёт сразу из своей очереди, мимо любого qdisc под собой. Если поставить tbf дочерним к netem, эти пакеты проходят мимо узкого места и его очереди. При `reorder 5%` полоса выходила на 6% выше узкого места, при `reorder 20%` — на 25%. Поэтому netem стоит на входе маршрутизатора (через ifb), а tbf — на выходе, и через узкое место проходят все пакеты.

Профиль меняется на месте (`tc qdisc replace`), так что промежутка без воздействий нет.

## Подготовка интерфейсов

- **TSO и GSO выключены** на всех veth, **GRO — на маршрутизаторе.** С ними veth передаёт склеенные пакеты до 64 КБ, и netem терял бы или задерживал такой пакет целиком, как один.
- **GRO включён у клиента и сервера**, то есть после всех воздействий, как у обычной сетевой карты. С GRO veth принимает пакеты через NAPI, одно кольцо, и выдаёт их по порядку. Без него veth ставит пакет в очередь того CPU, который его отправил. Пакеты, выпущенные netem то с одного CPU, то с другого, получатель обрабатывал параллельно, и одна задержка 20 мс без джиттера переставляла около 0,2% пакетов.
- **Соседи заданы статически.** Иначе ARP-запросы тоже шли бы через воздействия, и первые пакеты ждали бы ответа на ARP.
- **IPv6 выключен**, чтобы после поднятия интерфейса не было проверки адреса и лишних пакетов.
- **`ip_forward` задан явно** в каждом namespace: 1 на маршрутизаторе, 0 на клиенте и сервере. Новый namespace наследует IPv4-настройки хоста (`net.core.devconf_inherit_init_net`), и без явного значения стенд зависел бы от машины.
- MTU — 1500, как у Ethernet.

## Самопроверка (NET-4)

Перед серией стенд меряет сам себя и сравнивает результат с профилем. Если хоть одна величина вне допуска или замер недостоверен, `testbed check` завершается с кодом 1, и серия не стартует.

| Что | Как | Цель |
| --- | --- | --- |
| RTT | медиана `ping` от клиента до сервера | `rtt` |
| Потери | доля непришедших пакетов пробника | `loss` |
| Длина пачки | потерянные пакеты / число серий подряд идущих потерь; только при `loss_burst` | `loss_burst` |
| Перестановки | см. ниже | `reorder` |
| Полоса | `iperf3` по UDP | `rate × 1400 / 1442` |

**Допуск** — 10% от цели. Если цель равна нулю, нужен ровно ноль: так проверяется и NET-2 — при одном джиттере перестановок нет.

**Пробник.** Своя программа на Go шлёт пронумерованные UDP-пакеты по 64 байта сразу в обе стороны. Сокеты открываются прямо в namespace клиента и сервера. Темп — половина полосы узкого места, чтобы пробник не заполнял его очередь, и не больше 50 000 пакетов в секунду.

**Перестановки** считаются как число пакетов, которые нужно убрать, чтобы остальные шли по порядку: число пришедших минус длина наибольшей возрастающей подпоследовательности номеров. Пакет, обогнавший сотню других, считается один раз. Если считать переставленным каждый пакет, пришедший после пакета с большим номером (так в RFC 4737), один обгон дал бы сотню, и результат нельзя было бы сравнить с `reorder` у netem.

**Сколько пакетов.** Долю q, оценённую по n независимым пакетам, знаем со стандартным отклонением √(q(1−q)/n). Чтобы ошибка в три стандартных отклонения уложилась в 10% от q, нужно n = 9·(1−q)/(q·0,01), но не меньше 100 000. Тогда исправный стенд ложно проваливает одну проверку примерно в 0,3% случаев, а всю самопроверку — примерно в 1%. С 95% уверенности ложный провал был бы у каждой пятой самопроверки.

- Для 0,1% потерь это около 900 тыс. пакетов, для 0,5% — около 180 тыс.
- Перестановки считаются среди пришедших пакетов, поэтому n делится ещё на 1 − loss.
- Потери пачками зависимы: дисперсия доли растёт в (1+ρ)/(1−ρ) раз, где ρ = 1 − p − r — корреляция модели Гилберта между соседними пакетами. Для 2% пачками по 4 пакета множитель 6,84, и нужно около 300 тыс. пакетов.
- Длина пачки — среднее из n·loss/loss_burst пачек геометрической длины с относительным отклонением √(1−r). Отсюда ещё одно условие: n ≥ 900·(1−r)·loss_burst/loss.
- Тест `TestPacketsKeepFalseFailuresRare` моделирует потери так же, как netem, и проверяет, что с таким n ложных провалов меньше 1%, а с заниженным n их заметно больше.

**Число пингов.** Медиана n нормальных значений имеет стандартную ошибку примерно 1,2533·σ/√n, а RTT колеблется с σ = √2·jitter, потому что направления независимы. Отсюда число пингов на три стандартных отклонения в пределах 10%: для «Деградации» около 115, без джиттера — 20. Пинги идут не чаще раза в 4·jitter, чтобы не стоять в очереди друг за другом.

**Полоса.** iperf3 шлёт датаграммы по 1400 байт с нагрузкой 125% от полосы профиля, по очереди в каждую сторону. Если запускать обе стороны сразу, служебное соединение iperf3 застревает за встречным потоком.

- tbf считает байты кадра целиком, вместе с заголовками UDP, IP и Ethernet (42 байта), а iperf3 — только полезные данные, поэтому ожидается `rate × 1400/1442`.
- Потери не меняют результат: netem теряет пакеты до tbf, а оставшихся всё равно больше, чем пропускает узкое место.
- Берётся медиана посекундных интервалов получателя (`--get-server-output`) без первой секунды, пока заполняется очередь, и без неполного хвоста. Итоги iperf3 не годятся: получатель отсчитывает длительность теста по служебным сообщениям, которые задерживаются при потерях. Из-за этого итог занижался на 1–10%, а один раз оказался нулём.
- Если iperf3 сам упал (например, потерялась его служебная датаграмма), он запускается снова, до трёх раз. Низкий результат не повторяется.

**Недостоверный замер.** Пакеты могут теряться не из-за воздействий, а из-за самого замера. Поэтому до и после пробника читаются счётчики, и если какой-то вырос, отчёт помечается как недостоверный, а не как провал стенда:

- `RcvbufErrors` в namespace получателя — пробник не успевал читать;
- отбросы tbf — пробник перегрузил узкое место;
- столбцы drop в `/proc/net/dev` — переполнилось кольцо приёма veth;
- `/proc/net/softnet_stat` — переполнилась очередь пакетов какого-то CPU.

**Что показала самопроверка на эталонной машине:**

- потери, длина пачек и перестановки — в пределах 1–4% от цели;
- полоса совпадает с `rate × 1400/1442` до сотых долей процента;
- медиана RTT выше цели примерно на 0,4 мс при задержке от 2,5 мс в одну сторону. Это пробуждение процессора из глубокого сна (C-state), когда срабатывает таймер netem: под нагрузкой на всех CPU избыток исчезает (5,02 мс вместо 5,39 при RTT 5 мс). Для «Соседних зон» это 8% из 10% допуска. Ограничение C-states относится к настройкам машины (NET-5) и вместе с ними будет в sudo-скрипте.

## Проверки

- Юнит-тесты сверяют команды, которые строят стенд и применяют профиль, без сети. Они же проверяют формулы самопроверки, подсчёт потерь, пачек и перестановок и разбор вывода `ping`, `iperf3` и счётчиков ядра.
- Интеграционные тесты поднимают настоящий стенд.
  - Стенд: пакеты идут через маршрутизатор, медианный RTT по `ping` попадает в 10% от профиля, offload и GRO выставлены как надо, соседи статические, смена профиля заменяет qdisc, а ядро принимает каждый профиль из `profiles.yaml`.
  - Через узкое место проходят все пакеты, которые выпустил netem, в том числе переставленные.
  - Самопроверка проходит на совпадающем стенде, проваливается на несовпадающем и помечает замер недостоверным, когда пробник переполняет свой буфер.
- В CI эти тесты обязательны (`QRPC_TESTBED_REQUIRED=1`); на машине без user namespace они пропускаются.
